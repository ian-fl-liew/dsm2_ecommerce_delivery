# GCP / Google account setup

Constraint: during development, every team member replicates the pipeline using their own
Google account. 

What stays the same across everyone's project is the **artifact**: identical dataset/table
naming (`olist_raw` → `olist_warehouse` → `olist_reporting`, same dbt model names, same dlt
pipeline names). Only the GCP *project ID* differs per person — every script,
dbt profile, and pipeline in this repo already reads the project ID from one place
(`GOOGLE_CLOUD_PROJECT` in `config/credentials.env`), so nothing else needs to change per
teammate.

## One-time setup (every team member does this on their own account)

1. [console.cloud.google.com](https://console.cloud.google.com) → **New Project** with your own
   Google account. Name it anything (e.g. `olist-dsai-YOUR_NAME`) — the name only matters
   to you, since nothing else in the repo is hardcoded to a specific project ID.
2. Enable the **BigQuery API** for your project.
3. Authenticate as yourself (never a shared service-account key):
   ```bash
   gcloud auth login                       # personal Google account
   gcloud auth application-default login   # ADC used by dlt / dbt / SQLAlchemy
   ```
4. Put your project ID in `config/credentials.env`:
   ```
   GOOGLE_CLOUD_PROJECT=olist-dsai-YOUR_NAME
   ```
5. Run `bash scripts/setup_local_env.sh` — it points `gcloud config`, `ingestion/.dlt/secrets.toml`,
   and `~/.dbt/profiles.yml` at your project automatically.

## dev vs. prod, within your own project

`~/.dbt/profiles.yml` (generated by the setup script) still has two targets, both pointing at
*your own* project:

```yaml
olist_dbt:
  target: dev
  outputs:
    dev:
      dataset: dbt_dev_<your_handle>   # your personal draft schema
      ...
    prod:
      dataset: olist                   # -> olist_warehouse / olist_reporting
      ...                              #    in YOUR OWN project, once you're happy with a model
```

This is just good habit within your own project (`dbt run` won't clobber a "final" copy while
you're iterating) — it does **not** mean `prod` is shared across teammates. Everyone's `prod` is
their own project's `prod`.

## The submission project

Exactly one project is the team's actual deliverable — the one the Streamlit dashboard, Jupyter
notebooks, and the final presentation point to. Right now that's `ntu-bigdata-project`
(owned by Ian, billing already enabled — see the note below on why that's fine). Everyone else's
personal project is for individual development and verifying the pipeline works end-to-end on
their own account; it does not need to feed the submission project.

**The submission project is never updated by a manual `dbt run` from someone's laptop.** All
transformation is controlled from source code: a merge to `main` is what changes what the
submission project looks like, applied by `.github/workflows/ci.yml` (`dagster asset
materialize`, which runs both dlt hops and `dbt build` in dependency order — see
`orchestration/README.md`) on push to `main` or manual `workflow_dispatch` — no schedule, since
the source dataset is static. That's the only path that writes to `olist_raw` →
`olist_warehouse` → `olist_reporting` in the submission project. Nobody should have
`prod`-target credentials for the submission project configured locally — personal
`dbt run -t prod` only ever touches your *own* project (previous section), never
`ntu-bigdata-project`.

## Running the dashboard

Streamlit runs **locally only** — `dashboard/utils/bigquery_client.py`
just uses `google.cloud.bigquery.Client(project=...)`, which picks up your own ADC (`gcloud
auth application-default login`, already set up per the steps above). No separate service
account or key file needed — whoever runs the dashboard just needs `BigQuery Data Viewer` on
whichever project's `olist_reporting` they're pointing at (their own project, or the submission
project if they've been granted read access to it), which their personal Google account
already has for their own project.
